# react-core-skills

软件工程文档驱动开发准则。收到软件开发任务后，先识别所属场景并路由到对应必产文档链，逐阶段产出文档，**每阶段必须经用户门禁确认后才进入下一阶段**。文档是代码的蓝图而非事后补的说明，禁止代码与文档静默分叉。

## ⚠️ 强制执行规则（v0.16.6 强化 — 不遵守将导致任务失败）

收到本技能的调用结果后，必须严格遵守以下规则：

1. **每个阶段产出物完成后立即调用 `ask_user`**（除非用户在最近一条消息里明确写了「全部接受，继续」「不要问，直接做」「继续」之类的明确放行语）：
   - 阶段 0 开源调研后 → ask_user 确认结论
   - 阶段 1 PRD 后 → ask_user 确认功能范围
   - 阶段 2 交互文档后 → ask_user 确认交互流程
   - 阶段 2.5 HTML 原型后 → ask_user 确认视觉冻结
   - 阶段 3 系统设计后 → ask_user 确认技术方案
   - 阶段 5~8 每完成一阶段 → ask_user 报告进展

2. **`ask_user` 必须给出 2~4 个选项**（multiSelect=false），不要让用户自由输入。每个选项 label 一行、description 一段。
   - 参数名是 `suggestions`（不是 `options` / `questions`），每项结构：`{ label: string, description: string, recommended?: boolean }`
   - **绝对禁止**只给 `question` 字段而不给 `suggestions` 数组！只给 question 等于让用户自由输入，违反「门禁 + 选择」原则。
   - v0.16.x：工具 schema 已把 `suggestions` 升为必填（minItems=2, maxItems=4）。**引擎会在校验失败时拒绝并写一条 observation 让你重试**——不传 suggestions 不会让用户自由输入，而是浪费一轮迭代。必须遵守。
   - 正确示例：
     ```
     ask_user({
       question: "【阶段1 PRD 门禁】PRD 已产出（docs/01-prd.md）。功能清单 P0/P1/P2 是否齐全？",
       suggestions: [
         { label: "全部接受", description: "P0 12 项 + P1 8 项 + P2 5 项，认可，进入阶段 2 交互", recommended: true },
         { label: "P0 减半", description: "P0 保留核心 6 项，P1 暂缓，进度更快" },
         { label: "加 P0 项", description: "我再列几项必须做的（说具体哪些）" }
       ]
     })
     ```

3. **场景 A 阶段 4（编码）才开始写代码**。严禁在阶段 0~3 阶段产出文档期间写任何 `index.html` / `src/*.js` / `package.json`。即便用户说"做完整个游戏"，也是先文档 → 等用户拍板 → 才开始编码。

4. **门禁未确认绝不跳阶段**。即便 maxIterations 接近耗尽，也必须先 ask_user 让用户拍板，绝不擅自继续。

5. **阶段 0~3 中途若要快速完成合并**（PRD + 交互 + 系统设计合一份精简 doc），必须先 ask_user 确认「是否合并」，未确认前禁止合并。

6. **场景 A 默认走完整流程，不要直接跳过到编码**。如果觉得太重 → ask_user 让用户在「完整流程 / MVP 快速通道 / 关卡减半」中三选一。

## 0. 触发词与场景路由

收到任务后，按触发词识别场景并路由：

| 场景 | 触发词 | 路由目标 |
| --- | --- | --- |
| A 从 0 开始 | 从 0 开发 / 新项目 / 新功能 / 先出文档再写代码 / 先出设计稿原型 | 完整流程（阶段 0~8） |
| B 软件升级 | 升级 / 迭代 / 加功能 / 版本迭代 | 增量文档链 |
| C Bug 修复 | 修 bug / 修复 / 改一下 / 调整 / 小改 | 缺陷处理链 |
| D UI 设计 | UI / 改界面 / 设计 / 样式 | UI 专属链 |

**路由规则**：
1. 命中单一场景 → 直接路由。
2. 多场景冲突（如"给设置页加个功能"）→ 按用户最近一次明确表述优先；仍无法判定 → 向用户提问不超过 3 个最关键问题，不静默猜测默认场景。
3. 拿不准项目状态时：已有可运行产物且增量修改 → 默认 B；完整新功能或涉及 3 个以上模块 → 建议 A，用户坚持快速则走 B 并在汇报中注明。
4. 路由后向用户简要复述识别到的场景与即将执行的文档链，等待确认或纠偏后再推进。

## 1. 场景 A：从 0 开始（完整流程，阶段 0~8）

适用于新项目从零搭建、中大型新功能（预计改动 3 个以上模块）、用户明确要求按流程开发。核心原则：调研先行、文档先行、设计遵规范、原型先确认、接口有契约、缺陷可回溯、变更留痕、改后必测、交付即用。

### 阶段 0：开源调研
- 用 web-search / fetch-url 搜 GitHub 等开源社区（关键词中英文各一轮 + awesome 列表）。
- 评估 star 数与增长 / 最近维护 / license 兼容 / 技术栈匹配 / 代码质量与文档完整度。
- 结论三选一：直接使用（依赖/fork）/ 借鉴设计（架构/交互/数据模型）/ 确认自研；有高分项目优先借鉴并注明出处。
- 产出 `00-opensource-research.md`。门禁：用户确认调研结论。

### 阶段 1：PRD（产品需求文档）
- 必写：目标用户与场景、核心问题、功能清单（P0 必须 / P1 增强 / P2 远期，功能编号 F1/F2… 并带验收标准）、明确不做的范围、业务规则、依赖风险、成功指标。
- 信息不足先列假设标注【待确认】，并向用户提问不超过 3 个最关键问题，不在未确认前提下编造功能。
- 产出 `01-prd.md`。门禁：用户确认 PRD 要点。

### 阶段 2：交互文档
- 产出：页面/界面清单、用户主流程图（文字或 mermaid）、每页元素与五态（默认/加载/空/错误/成功）、关键交互规则（手势/跳转/反馈）、设计 token（色彩语义/字号阶梯/间距基准/触摸目标）。
- 设计 token 以 CSS 变量形式落地，编码引用不写死数值。
- 从开源借鉴的交互设计注明来源。
- 产出 `02-interaction.md`。门禁：用户确认交互流程。

### 阶段 2.5：HTML 高保真原型（条件触发）
**条件触发规则（用户裁决）**：
- 任务涉及前端交互修改 → **必产** HTML 高保真原型，经用户确认后冻结为视觉基准，才允许进入阶段 3。
- 任务为后端/纯逻辑/数据层改动（无前端交互）→ **跳过**，并在产出物注明"本期未做 HTML 原型"+ 视觉偏差风险提示。

原型硬性要求：
- 纯静态单文件零依赖（不引用 CDN/外部框架）。
- 全部样式引用 `:root` CSS 变量，禁止写死数值。
- 每页内置五态切换器；真实感中文假数据；移动端套 375px 设备壳；页面可跳转串联主流程。
- 暗色模式 token 出双份。
- 原型只做"看上去、点起来像真的"，不写真实业务逻辑。

原型冻结门禁：呈现原型并附审查话术（①总览配色字号 ②每页五态 ③主流程从头点一遍），用户确认后冻结。用户提修改 → 改原型 → token/交互规则有变则同步修订交互文档（升小版本 + 变更记录）→ 再次呈现确认。

### 阶段 3：系统设计
- 产出：技术选型与理由、架构分层图、模块划分与职责、数据模型（表结构/字段）、接口定义（路径/入参/出参/错误码）、非功能设计（性能/安全/异常处理）。
- 每个接口/Service 方法写清"功能职责一句话 + 输入 + 输出 + 错误场景"作为编码注释对照标准。
- 个人项目从简但数据模型和接口契约必须写全。
- 产出 `03-system-design.md`。门禁：用户确认技术方案。

### 阶段 4：编码
- 按系统设计拆任务（一模块一任务）；严格按文档实现。
- UI 实现必须对照已确认 HTML 原型 1:1 还原（布局/token/五态以原型为准，不随手取近似值，因技术限制偏离需逐项说明）。
- 接口与 Service 注释要求：功能职责/参数含义/返回值/抛出的错误；复杂逻辑写"为什么"不复述代码。
- 发现设计缺陷走缺陷回溯（见 §6）。
- 编码完成后汇报：功能清单 / 与文档偏差及原因 / 期间文档回溯记录。

### 阶段 5：功能测试
- 执行顺序固定：先冒烟 → 再详测 → 后验收，不可颠倒合并。
- 先冒烟：产物能构建能启动、P0 主链路 happy path 逐条过、关键集成点正常，任一失败立即停止打回编码重跑，冒烟全绿前禁止铺开详测。
- 再详测：对照 PRD 逐项验正常/边界/异常/错误处理/数据一致性/接口契约；端到端主流程与交叉场景必须覆盖。每缺陷记录复现步骤/预期实际/严重级别（阻塞/严重/一般/建议）。
- 后验收：准入自查 → 准出核对 → 用户验收 UAT（可运行产物 + 验收走查路径 + 用户实际点一遍明确确认）→ 验收结论。
- 产出 `04-function-test-report.md`。门禁：冒烟全绿 + P0 全过 + 阻塞/严重清零 + 用户验收确认。

#### 阶段 5 · 硬约束（v0.16.6+ 强化 — 不遵守报告作废）

1. **不接受「静态走查 / 代码阅读 / 配置完整性」作为 PASS 证据**。前端产物必须用 CDP 实际加载、捕获 console 与异常、跑通主链路；后端产物必须起服务、跑接口调用。前两类"证据"全部判定为"未测试"，对应项标 **UNTESTED**（不是 PASS）。
2. **每条 PASS / FAIL 必须附三类证据**：
   - **代码引用**：`path:line` 指向实现位置（必填）
   - **运行时证据**：CDP 控制台无该功能相关报错 / DOM 探针截图 / 接口实际返回
   - **操作链路**：用户/键盘/鼠标从入口到该功能的完整事件序列
3. **冒烟不通禁止铺开详测**。冒烟未全绿前，详测报告里所有 P0/P1 项标为 **BLOCKED（冒烟未过）**，不得标 PASS。
4. **修复与测试同步**：冒烟发现的 bug 必须在同一阶段内修完并复测，复测通过的项才能从 BLOCKED 改回 PASS；不可"记录缺陷但交付"。
5. **产物加载工具**：前端单文件 index.html 用 CDP（Node 脚本 `_smoke_test.mjs` 已放在 `/Users/gongzheng/ai/ArkWork/app/`，Agent 可直接 `node _smoke_test.mjs <cdp-ws> file://.../index.html` 拉真实 boot 状态 + 异常列表 + 截图）。
6. **报告末尾必须附「运行时证据汇总」**：列出本次实测用到的 CDP 输出、控制台日志摘要、异常清单、截图路径。无此节则报告未达交付标准。

### 阶段 6：UI/UX 验证（如适用）
- UI 测试：对照交互文档逐页面验证（元素齐全/状态流转/交互反馈/设计规范落地），同时逐页与已确认 HTML 原型比对，偏差即缺陷。产出 `05-ui-test-report.md`。
- UX 走查：真实用户视角走查（学习成本/操作路径/文案/一致性/容错防呆）；区分"缺陷"（必须修）与"建议"（列优先级由用户决定）。产出 `06-ux-review-report.md`。
- 门禁：交互文档定义的流程与状态全部验证通过。

### 阶段 7：部署交付
- 按项目类型构建/打包，产出用户可直接使用的产物，不允许只给源码。
- 部署设计文档（如适用）：环境清单（dev/int/uat/prod）、部署拓扑、CI/CD 流水线、Runbook。
- 交付物含：构建产物 / 快速开始说明 / 对应文档版本号 / 遗留问题清单。

### 阶段 8：运维沉淀与手册
- 维护 Changelog（按版本分组 Added/Changed/Fixed/Removed）。
- 沉淀 Runbook（常见故障处理）。
- 产出 README / 使用手册：项目说明、快速开始、目录结构、功能清单、遗留问题、后续计划。
- 版本迭代转场景 B；线上缺陷转场景 C。

### 小型功能边界
允许将阶段 1~3 合并为一份精简设计文档，HTML 原型精简为单个 index.html（token 展示板 + 核心页面同页切换），但必须动手前向用户说明并征得同意。阶段 0 不可省略，只做加速版（30 分钟内）。

## 2. 场景 B：软件升级（增量文档链）

适用于已有可运行项目的升级 / 版本迭代 / 加功能。采用"增量"原则：只写与本次变更相关的部分，复用既有文档基线，避免全量重写。

必产链（每步门禁确认后才进入下一步）：
1. **变更申请/影响分析**：变更动机、范围、受影响模块、兼容性影响、风险项（依赖既有 docs 基线定位受影响文档）。
2. **增量 PRD**：仅本次新增/变更功能（编号延续既有 F 编号体系），引用既有 PRD 基线，不重写未变更部分。
3. **增量设计**：仅受变更影响的架构/数据模型/接口；数据模型和接口契约必须写全。
4. **API 变更**（如有）：接口变更时同步更新接口文档与代码注释，三者（文档/注释/实现）一致。
5. **回归测试**：三层回测（修改点验证 / 受影响功能回归 / 整体回归），确认无"修 A 坏 B"。
6. **发布说明 + Changelog 更新**：语义化版本号 + 新功能/修复/已知问题/兼容性；Changelog 按版本分组追加。

发现既有文档与实现不一致 → 走缺陷回溯（见 §6）。变更影响范围超出预期（如涉及 3 个以上模块）→ 提示用户评估是否升级为完整流程（场景 A），由用户决策，不擅自切换。

## 3. 场景 C：Bug 修复（缺陷处理链）

适用于线上/测试环境缺陷修复。遵循"改后必测"。

必产链（每步门禁确认后才进入下一步）：
1. **Bug 报告**：复现步骤、预期/实际、严重级别（阻塞/严重/一般/建议）、环境。
2. **根因分析 RCA**：现象、根因、影响范围、修复方案、预防措施。根因无法直接定位时不臆断，列出候选根因 + 验证方法，向用户说明并确认后再修复。严重缺陷可选产出复盘报告。
3. **修复说明**：改动点 + 涉及文档同步（功能行为/接口契约变更时同步修订受影响文档，升小版本 + 变更记录追加）。
4. **回归验证**：修改点验证必做 + 关联回归必做 + 整体回归仅核心链路。
5. **Changelog 追加**：按版本分组追加 Fixed 记录；纯 bug 修复只升小版本 + 变更记录追加。

修复过程中发现根因来自上游设计文档缺陷 → 走缺陷回溯（见 §6）。

## 4. 场景 D：UI 设计（专属链）

适用于 UI 设计 / 界面改版需求。先判定是否涉及前端交互修改（用户裁决）：
- 是 → 走完整场景 D 链（含 HTML 原型必产）。
- 否 → 跳过原型，产出物注明"本期未做 HTML 原型"+ 视觉偏差风险提示。

必产链（每步门禁确认后才进入下一步）：
1. **设计规范/token**：主色/语义色/中性色阶/字号阶梯/间距/圆角/阴影/触摸目标（44px iOS/小程序、48dp Android、44px Web）；暗色模式出双份 token。
2. **交互文档**：覆盖 PRD 全部 P0/P1 功能；每页面五态写全；交互规则（手势/跳转/反馈）。
3. **HTML 高保真原型**（前端系统必产）：见阶段 2.5 硬性要求；token 1:1 转写 `:root` CSS 变量。原型冻结为视觉基准。
4. **UI 测试**：逐页与已确认原型比对（布局/配色/字号/五态/交互反馈），偏差即缺陷；设计规范落地核查（对比度 ≥ 4.5:1、触摸目标达标）。
5. **UX 走查**：真实用户视角；区分缺陷（必修）与建议（列优先级由用户定夺）。

设计 token 缺失时禁止"随手取色/随手取值"，先补齐 token 表再继续。原型修改涉及 token/交互规则变更时同步修订交互文档（升小版本 + 变更记录），不静默只改原型。

## 5. 文档元信息规范与版本化目录

### 文档头部元信息（每份正式文档必填）
- 文档名称、版本号（语义化 vMAJOR.MINOR.PATCH）、日期、状态、关联文档、变更记录表。
- 状态流转：草稿 → 已确认 → 已修订 → 已冻结。

### 版本化目录约定
- 产出物写入用户指定目录（默认 `docs/vX.X/`，可由用户指定如 `docs/`、`products/`）。
- 目录结构：`00-opensource-research.md` / `01-prd.md` / `02-interaction.md` / `prototype/` / `03-system-design.md` / `04-function-test-report.md` / `05-ui-test-report.md` / `06-ux-review-report.md`。
- 大版本迭代新建 `vX.0/`，**禁止覆盖旧版本文档**；小修订升小版本（v1.0 → v1.0.1）不新建文件夹。
- 项目已有 docs 结构则叠加版本文件夹，保持兼容。
- 全部文档纳入 Git 管理（Docs as Code）。

### 变更记录表
每次修订追加一行：日期 / 原因 / 改动点 / 影响范围。

## 6. 门禁确认

- 每阶段文档产出完成后，向用户发出门禁确认提示：阶段名 + 产出物路径 + 要点总结 + 待确认项清单。
- 用户确认（通过）→ 进入下一阶段；用户驳回（附意见）→ 定位文档修订（升小版本 + 变更记录追加）→ 重新提交确认。
- **用户未确认前，不推进任何下游阶段。** 可并行整理下一阶段准备材料但不在产出物上落盘。
- 驳回无意见时向用户请求具体修订意见（最多追问 1 次），不猜测修订方向。
- 阶段跳转：禁止跳阶段；用户明确要求跳过某阶段（阶段 0 除外只可加速）确认后跳过并在产出物中注明，不得静默跳阶段。

## 7. 缺陷回溯机制

任一阶段发现上游设计文档缺陷，或代码与文档不一致（静默分叉），按闭环处理：

1. **定位**：通过文档头部元信息"关联文档"字段向上游定位问题文档。
2. **修正**：修订问题文档（升小版本 + 变更记录表追加：日期/原因/改动点/影响范围）。
3. **同步**：检查下游受影响文档（接口变更 → 接口文档；token 变更 → 交互文档/原型），逐一同步修订。
4. **告知**：向用户汇报（改了什么 / 同步哪些文档及小版本 / 影响范围）。
5. **继续**：回溯完成后继续原流程；回溯记录归档供追溯。

回溯是正常环节而非返工失败。禁止代码与文档静默分叉（改了代码不改文档 / 改了文档不告知）。文档无法定位时不静默猜测，向用户询问/在项目文档树中检索，定位后再修订。文档-代码不一致时以文档为 source of truth 判定：文档合理则修订代码，文档过时则修订文档，并在变更记录中注明判定理由。

## 8. 渐进式披露与约束

- 本 SKILL.md 主文件 ≤ 500 行，长参考材料放 references/ 按阶段按需读取，不一次性加载全量。

## 9. 产物保存位置

- 所有文档产物保存到**用户指定目录**（默认 `docs/`，也可为 `products/` 等），由用户在任务开始时指定或按项目约定。

## 10. 交付与运维沉淀（README / 使用手册生成）

任务达到交付里程碑（场景 A 阶段 7 / 阶段 8，或场景 B 的发布阶段）时，**自动生成两份用户产物**并与文档链同目录保存：

## 11. 执行约束速查

- 先理解再修改：动手前先读必要文件，了解结构与模式，模仿现有代码风格。
- 最小改动：只做任务直接要求的改动，不重构范围外代码、不添加多余注释/类型标注。
- 不过度工程化：不为一次性操作创建抽象，不为不可能发生的场景加错误处理。
- 改后必测：修改点验证 + 受影响回归。
- 文档/注释/实现三者一致，禁止静默分叉。
