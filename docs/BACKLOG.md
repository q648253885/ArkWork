| ㉟ | **修根因 ≠ 清现场：当"产物目录自身会被打包"时，必须有一条扫现场的用例。** 这条纪律针对的是**改动顺序**造成的静默残留 —— 你修好了产生脏数据的那段代码，但那段代码**已经写下的**文件不会自己消失，而构建/打包链默认**不清产物目录**（`electron-vite build` 不清 `out/`；`electron-builder` 把 `out/` 整棵收进 `app.asar`）。于是脏数据一路随包出货，且三个"都不是"同时成立：字节小、不报错、不进功能路径 → **没有任何机制会碰到它**。规则：① 凡"构建产物目录会被收进交付物"的项目，加一条**扫现场**断言（本仓 TC-CLEAN-008：`out/` 不得含 `.arkwork*`）；② 断言必须**先自证看的是对的那棵树**（先断言含 `main` + `renderer`，否则路径写错会得到一个永远绿的用例）；③ 交付前核一次**产物白名单**（本仓 evidence 02 §1.2 的 asar 非依赖条目表）—— 出货物里"多了什么"与"少了什么"同样重要。反例（D194）：`dev/b2-smoke.ts` 早期用 `resolve(__dirname,'..','..','.arkwork',…)` 把冒烟结果写进 `out/.arkwork/`，源码后来改成 `app.getAppPath()`（注释都写明了），但那 354 B 的 `ok:false` 残留跟着此后每一次打包出货 | v0.39.0（D194） |
| ㊱ | **证据必须能指认来源：「日志模板」不是「日志」。** 放在纪律区而不只是"AI 行为守则"，是因为它直接决定**逐版归因能不能复原**（纪律⑤/㉕ 的前提）：证据只有两种合法形态 —— ① **可复跑的命令 + 它跑出来的真实输出**；② **可打开的产物 + 它的真实字节**（asar 条目 / TAP 日志 / `Info.plist`…）。**绝不允许**用"这类日志通常长这样"去补现场 —— 本仓尤其危险，因为 `logs.jsonl` 的每一条都有固定格式，格式极易被反向"脑补"成现场叙述。比没有证据更坏的是**看起来有证据**：下一位读者会以为"已经实机复现过"，从而跳过真正的验证，而本版所有"实机"结论恰恰以"有没有样本"为前提（L-39-06）。落地要求：① evidence 文件顶部写**证据口径声明**（全部结论来自可复跑命令或可打开产物；推测一律进"遗留/观察"）；② 一旦发现混入脑补内容，**整节删除重写**并在文末留删除记录（承认比掩盖便宜） | v0.39.0（打包复查期） |
| ㊲ | **补上了「入口」不等于补上了「出口」：带重试的容错机制必须显式写出「重试**用尽**之后怎么办」。** 本仓反复出现的形态是：一个防御机制只写了**触发条件**与**重试次数**，而"重试仍然失败"这一支**没有 else** —— 失败态于是原样流回主流程，被下游当成**正常结果**处理。它比"缺功能"隐蔽得多：判据在场、次数有上限、既有守卫用例还全绿（因为那些用例钉的是**入口接线**），只有把**端点行为**做成确定性输入才看得见。规则：① 凡 `for (retry…)` / `while (attempt…)` 这类块，**紧跟其后必须有一个显式的失败出口**（暂停 / 失败 / 占位，三选一，并在同一条注释里写明为何选它）；② 守卫用例必须**成对**：入口类（判定 / 次数 / 位置）+ **终局类**（用尽后发生了什么，且断言"**不许**流到哪个分支"）；③ 判断"该停还是该放行"的依据取自**被复用判定的原语义注释**（本仓 `isIncompleteLlmResponse` 明写"必须重试或失败，**不能算完成**"），而不是就近找一个看似合理的收尾。反例（D197）：空响应补试只有入口，补试用尽后空响应顺着「未调工具 ✓ + 清单无未完成项 ✓ + 未截断 ✓」三条判定被当成**最终答复**，用空 summary 把任务封成 `completed` —— 用户看到一条空白「答复」而任务已 done。**同一形态的第二处**：`summary` 兜底链写成 `?? safeSlice(thought)`，两级**都**可能为空 → 兜底链等于没有兜底 | v0.39.0（D197） |
| ㊳ | **写了「给将来用的」持久化字段，就必须写出它的消费者**——否则是**静默丢失**，而且骗过所有「写入侧」用例。** 本仓形态：引擎有 **9 处**暂停点把提问写进 `Task.pendingAskUser`，并且既有守卫白纸黑字断言「必须写 pendingAskUser，**否则重开任务时问题丢失**」—— 即这个字段的**存在理由**就是"重开时要能看见"。但渲染层只认**活体事件**（`store.askUserQuestion`，初值 `null`、切任务时显式清空），全仓 `grep -rn pendingAskUser src/renderer` = **0 命中**。结果：当场看着它暂停一切正常，**刷新 / 重开 / 切走再回来**就只剩一句无因由的「已暂停 · 等待你的指令…」，五处精心写的人话（D52/D65/D160/D168/D197）全部丢失。规则：① 任何"为了跨会话 / 跨重开而持久化"的字段，落地时必须同时交付**读取方**，并且用例要断言"**有人读**"（消费者数量下限，防被整段删除）而不是只断言"有人写"；② 合并两个来源（活体 ∪ 持久化）的优先级判定必须抽成**纯函数**并真值表钉死（本仓 `resolveAskUserQuestion`，渲染层首个 `@@ARKWORK-PURE@@` 真执行用例组）；③ **实机验收的价值恰在这里**：静态看「引擎写了 + UI 有门禁组件」像是通的，只有真的刷新一次页面、再 `document.body.innerText` 直查关键词，才知道那段话**根本没到用户眼前**（`连续` / `空响应` / `不会被标记完成` 全为 false）。反例（D198）。** |
| ㊴ | **「新开一条独立通道」必须同时交付节流三件套（预算 / 间隔 / 幂等），且**预算判定必须优先于一切豁免**。** 本仓形态：给弱模型开的兜底通道（规划通道 v0.39.0、清单操作通道 v0.40.0）天然是「额外一次 LLM 调用」，没有预算就会变成「每轮都问」（token 与时延翻倍）。但真正的陷阱在**豁免**：为了「紧急场景别被节流卡住」而加的 `force`（如空回合兜底、一次性收尾），如果写在预算判定**之前**，兜底就会变成新的空转源 —— 空响应一轮一次、`force` 一路放行，直到 `maxIterations`。规则：① 判定顺序固定为 **预算 → 间隔 → 幂等 → 放行**，`force` 只豁免"间隔"这一层；② 预算阈值必须是**导出常量**（唯一事实源）并被真值表用例直接引用，禁止散落字面量；③ 幂等（指纹未变就不落库）只对"要新文本"的操作生效 —— 要**判定**的操作（`complete` / `cancel` / `replan`）不受限，否则语义会被静默吞掉。用例必须有一条专门断言"预算耗尽后 `force` 也被拦"（v0.40.0 TC-OPS-003）。 |
| ㊶ | **「引擎 ↔ 模型」接口的边界形态，必须至少被真实模型跑过一次。** 纯单测与静态审查只能验证「逻辑对不对」，验证不了「接口形状覆不覆盖真实世界」。v0.40.0 真机四轮**连抓三条**同族缺陷，每一条都符合「单测直接构造输入 → 永远构造不出真实输入」：① **D204** —— 单测里 `signals` 是手写的，真实世界里它由 `loop` 赋值，而赋值点**被无工具分支的十几处 `continue` 跳过**（测的是函数，坏的是接线）；② **D205** —— 真实模型会把同一段 JSON **说两遍**、会用 `[running] 文本` 前缀，这些形态**只有真模型会生成**（人工写测试用例时脑子里不会有它们）；③ **D206** —— 指标（清单变更次数、终态）**全部达标**，只有看**内容**才发现五项被全标 `done` 而任务零产出（**静默假成功**，D197 同族）。规则：① 新写的「引擎→模型」prompt / 解析 / 触发，收尾必须跑一次真模型端到端（`.app` + 可用的最弱模型），并把**读数表**写进 evidence；② 指标要看**内容**不只看**计数** —— 「变更次数多」在弱模型场景下可能正是**幻觉活跃**的信号；③ 真机验收**每轮修完都要重跑**（v0.40.0 是四轮 → 三条缺陷），不要因为「逻辑上这次肯定对了」而跳过。反例备忘：本仓 D198（人话没渲染）与 D204/D205/D206 是**同一族**，四次都是真机抓出来的。 |
| ㊵ | **解析器的「安全降级」默认值必须与「放行开关」分离：默认**零变化**，放行只给确实需要它的调用方。** 本仓形态：解析器的 S1 不变量把解析出的 `done` 一律降级 `todo`（D181，当时是对的 —— 防止模型自证完成）。但 v0.40.0 的清单操作通道要求模型输出**完整**清单并「保留已完成项」，若沿用无条件降级，模型**原样返回当前清单**就会把已完成项**回退成待做** —— 清单倒退，与"让清单推进"的目标正好相反。规则：① 安全不变量要保留，但必须做成**显式参数**（本仓 `parsePlannerOutput(raw, { allowDone })`，默认 `false`），既有两个调用方行为零变化；② 放行范围要**逐个操作论证**并在代码注释里写明（本仓只放行 `update`/`complete`：`create` 是工作未开始、`replan` 的新 done 必须由执行事实产生）；③ 反向核验的注入点必须打在**入口**而不是下游函数的默认参数上 —— 入口算出布尔后显式传参，改下游默认值会被覆盖，首轮核验因此误判为"用例失效"。 |
